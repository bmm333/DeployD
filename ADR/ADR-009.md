### ADR 009: Adopting a Tool Based Agent with Deterministic validation

**Data:** 18 Sept 2026
**Status:** Accepted

## Context

DeployD architecture (Tire 1& 2) gathers events in a graph and recovers historical ones through hybrid retrival. The final Tier 3 needs to present a root cause to the engineer.

Giving Raw data to an LLM and ask it to deduce the root cause of an incident, would introduce a risk that is not acceptbale. With no constraints the model would invent dependencies, mention fictional runbooks, and assume cluster states (unverified ones). A good but fake hypothesis is worse than no hypothesis.

## Decision

We decided to implement Tire 3 not as an Passive LLM, but as an **Agent Tool Using** based on Agno framework, introducing Deterministic guardrails.

This decision is split into 4 technical components in the branch `feat/agno-agent`:
1- **Strict Tooling**: The agent dose not have the possibility to execute arbitrary commands, nor access the system freely. It can interrogate only `ComponentRegistry` through the defined tool `check_component_dependencies` (which executes deterministic matching of Versions) and use `search_runbook` per gli storici.
2- **Structured Output**: The output is forced through Pydantic schema (`AgentDiagnosis`), defined in `deployd/application/dtos/diagnosis.py`. The DTO lives in the Application layer (not in the Adapter) so the Orchestrator can reference it without violating Clean Architecture dependency rules.
3- **Evidence Validator:** Implemented `_validate_evidence` method inside AgnoGroqAgent class. This is an outgoing filter , matching ID's mentioned by the LLM , with a temporary set of traced ID's  which the tool returns, or the ochestrator passed in that specific session. Each and every ID mentioned by the LLM that is not present in this Temporary Set is stripped off from the diagnosis before it reaches the final user.
4- **AgentPort Contract**: `AgentPort.diagnose()` returns `AgentDiagnosis` (not a plain string). The Orchestrator wraps this into `DiagnosisResult.structured_diagnosis` for Tier 3, keeping `remediation.summary` populated from `AgentDiagnosis.root_cause`. The protocol also exposes `follow_up(session_id, message)` and `last_session_id` for multi-turn.
5- **Demo & Offline Fallback**: To guarantee a working end-to-end demo without external API dependencies, `EventSimulator` acts as the incoming adapter. It transparently falls back to a `StubAgent` (which returns a deterministic string and a dummy structure) when `GROQ_API_KEY` is not present, displaying `[MODE: offline/stub]` to avoid confusion.

## Consequences

**PRO**:
- Technical Halucination risks are lowered ( never 0 )
- The validator guarantees that the LLM cannot mention inexistent runbooks

**CON**:
- **Latency**: The workflow requires squenciale calls before the tool generates the final diagnosis
- **Rigidity**: The model is strongly limited. If the root cause is outside the covered tool's domain (like IAM) the agent dose not have the tools to investigate that.
- **UX**: IF the LLM bases its reasoning on top of an invented runbook, the validator will only take off the ID's leaving the diagnosis with orphane referals.

## Update — DID-33 agent hardening (7 Oct 2026)

The guardrails above were partly prompt-based. They are now enforced in code:

- **Tool I/O contracts**: the four read-only tools (`search_runbooks`, `get_runbook_detail`, `check_component_dependencies` and the new `get_fsm_health`, which replays the investigation's own events through a fresh `ProcessHealthFSM`) validate their arguments with Pydantic input models and answer with Pydantic result models serialised as JSON (`deployd/adapters/outgoing/ai/tool_models.py`). Bad arguments, unknown IDs and results over 1,500 characters come back as `{"error": ...}`; JSON escaping keeps untrusted runbook text inside its field.
- **Run limits**: Agno refuses tool calls beyond `TOOL_CALL_LIMIT` per run; every Groq call runs at a low temperature with a bounded output budget.
- **Validator on free text and follow-ups**: any `RB-*` / `compat-*` token in `root_cause`, `reasoning` or `recommendation` that is not in the session's evidence set is replaced by `[unverified reference removed]`. Follow-ups answer with a structured schema (answer, confidence, citations) and go through the same validator; the evidence set is per session (retrieved candidates plus IDs its tools showed).
- **Fail-closed on unverifiable answers**: if no citation survives validation, the orchestrator discards the answer. The gate decision stays FULL (the LLM was called), but the engineer sees only the causal chain, and the decision trace reports `answer_discarded`.

**Consequences**: the "orphan referrals" CON above is mitigated: an invented ID never reaches the UI, and an answer that rests only on invented evidence is withheld. A residual risk remains: an answer can cite one valid runbook while its prose leans on an invented one; the ID is removed, the prose is not. A structured follow-up costs one extra parser pass when tools are enabled (Groq rejects JSON mode together with tool calling).
