### Graph Trasversal Strategy
## Status - Proposed
## Context
DeployD performs root cause implementing four distincit phases

1- Observation: what raw evidence do we have? (Human observation?,CoreEvent)
2- Detection: what relationships or anomalies can we extract from the evidence?
3- Graph Traversal: Given an starting point in the incident graph, what subgraph is relevant to gather context for hypothesis?
4- Retrival: which historical incidents help us resemble what we found (RAG jira ticket DID-7)

This ADR addresses only problem 3. Traversal operates on relationships that already exist on the graph, so it cannot create by itself a relationship that wasn't already created.

For example: Deploy->Config Change->DB_Conection->Data_Written where DB_Conection
points to a test db, while the env is production, traversal alone cannot discover that this is wrong. This requires evidence such as prod->should_use->prod_db and service->uses->test_db. Only once both edges exist a determinisce rule can say expected_Dependency != actual_dependency -> CONFIG_DRIFT. The rule belongs to Detection not Traversal.

## Decision
DeployD uses constrained BFS as the single traversal algorithm, parametrized by a traversa policy rather than implemented as separate algorithm per each type of traversal

Traversal Policy constrains:
- hop limit
- edge type(s) allowed
- edge direction
- temporal window
- optionaly: componenet/dependency scope

The traversal modes we had identified during design are not four separate algorithms, but they are four policies over the same BFS:

Mode            Policy Configuration                       Answers
Neighbourhood   any edge type,k hops,both directions       What happend around this event
Causal          CAUSED edges only, fwd direction only      What chain of causes led here?
Temporal        Ordered by timestamp, no type filter       In what order did this events occour?
Dependency      DEPENDS_ON edges only, expand outwards     What else could have this failure affected or been affected by?

Example (neighborhood, k=2,starting from PROCESS_CRASH):
PROCESS_CRASH <- DEPLOY <- COMMIT PROCESS_CRASH -> HEALTH_CHECK_FAIL -> SERVICE

Example (temporal): t1: deploy -> t2: config change -> t3: crash -> t4: restart

Example (dependency): checkout -> DEPENDS_ON -> payment -> DEPENDS_ON -> redis -> DEPENDS_ON -> network A checkout failure expands into this dependency neighborhood, not just checkout node itself.


## Consequences

### Positive:
- One traversal function to implement, test and reason about.
- New Implementation questions become new policy configs, not new code to develop and maintain.
- Keeps Traversal decoupled from Detection

### Negative accepted trade-offs:
- A generic BFS is not very performant for large graphs, we are accepting this for now as per incidents with low hundred of nodes per incident otherwise it will not scale.
- Policy misconfig: silently changes investigation quality rather than failing loudly, needs test converage per policy not just algorithm.

### Alternatives Considered
A dedicated algorithm per traversal type (separate causal-chain walker, separate dependency walker, etc.) — rejected: the four modes share the large majority of their logic (visited-set tracking, hop counting, edge filtering); only the filter/ordering predicate differs. Maintaining four implementations would mean fixing the same bug four times.
Full graph algorithms (Dijkstra/shortest-path, PageRank-style ranking) — rejected for MVP: incident graphs are small, these add complexity and interpretability cost that constrained BFS doesn't have, and a single shortest path isn't necessarily what an investigation wants — the goal is surfacing all plausible causes within N hops, not the one shortest one
