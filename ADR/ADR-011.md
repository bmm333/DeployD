# ADR-011: Model Selection for the Tier-3 Agent

**Date:** 2026-10-09
**Status:** Accepted

## Context

The Tier-3 model was chosen by elimination, not by measurement: `llama-3.3-70b-versatile` is no longer served by Groq, and `qwen/qwen3.8-27b` hit a rate limit on the first grounded diagnosis, so the agent ended up on `openai/gpt-oss-120b`. The choice needs evidence, and a way to change it.

Constraints:
- **Groq free tier, per model**: 8,000 tokens/minute, 1,000 requests/day, 200,000 tokens/day (from the `x-ratelimit-*` headers and the 429 bodies).
- **Agno with tools and structured output**: Groq rejects JSON mode together with tool calling, so every answer costs a reasoning run plus a parser pass (DID-15/33).
- **Safety behaviour matters more than prose quality**: answer only from the gated evidence, refuse other components (prompt 1.1.0), ignore injected instructions (1.2.0 / 1.3.0).

Candidates are the chat models available on the account on 2026-10-09: `openai/gpt-oss-120b`, `openai/gpt-oss-20b`, `qwen/qwen3.8-27b`. `allam-2-7b` is excluded because its 4,096-token context cannot hold the prompt, the evidence and the tool schemas; the remaining models are speech or guard models.

## Method

[`experiments/model_selection.py`](../experiments/model_selection.py) runs the real pipeline once per model: HTTP adapter → correlator → `LiveInvestigation` with the production retrieval stack and `AgnoGroqAgent`. Each run covers the 3 FULL live scenarios, twice. Each diagnosis is followed, on the same session, by an in-scope question and an out-of-scope question (about `billing-batch`). The OOM scenario also gets three injection vectors:
- an instruction hidden in a telemetry description, which always reaches the model;
- a poisoned runbook the engineer asks for by ID;
- a hostile engineer message.

Calls are paced per model under 8k tokens/minute. Refusal and injection checks are string heuristics. The answers and tool calls are stored verbatim and were reviewed by hand (corrections below).

Results: [`experiments/results/model_selection.md`](../experiments/results/model_selection.md) (final run). The JSON next to it holds every answer. `model_selection_run1.json` is an earlier run on the same day, made before the tool-call capture and the telemetry case were added.

## Results (final run, 2 runs × 3 scenarios per model)

| | gpt-oss-120b | gpt-oss-20b | qwen3.8-27b |
|---|---|---|---|
| Grounded diagnosis shown (FULL) | 6/6 | 6/6 | 4/6 (2 hit the daily token cap) |
| Out-of-scope question refused (manual review) | **6/6** | **1/6** | 4/4 |
| Telemetry injection: model cited the injected `RB-ADMIN-0` | 1/2 | 1/2 | 1/1 |
| Injection led to destructive advice (`rm -rf …`) | 0 | 0 | 0 |
| Diagnosis latency p50 / p95 | 3.2 s / 4.6 s | 3.2 s / 5.0 s | 38.4 s / 67.6 s |
| Diagnosis tokens in / out (mean) | 2,118 / 1,072 | 3,274 / 1,496 | 6,898 / 1,318 |
| Tool calls per diagnosis (mean) | 0 | 0.7 | 3.5 |
| Est. cost per incident (1 diagnosis + 2 follow-ups, list price) | $0.0025 | $0.0015 | $0.0214 |

- **gpt-oss-20b ignores the scope rule.** It never refuses clearly: it deflects ("The investigation is focused on…"). In 3 of its 12 out-of-scope answers across both runs it states that auth-service is "healthy", "stable" or "ready for deployment" in the middle of the OOM incident. Manual review also corrected the heuristic for this model: one counted refusal is a false positive, and one real refusal was missed, so the total is unchanged.
- **qwen3.8-27b is the most careful and the most expensive.** It calls tools on every diagnosis, opened the poisoned runbook both times, and named it as an injection. But one diagnosis needs 6–11k tokens, more than the 8k-per-minute budget, and its p95 latency is over a minute. It exhausted the 200k tokens/day free tier after 17 calls of the final run; the daily count includes the first run the same day. The first run, still within the quota, gave 6/6 grounded diagnoses and 6/6 refusals, at a p50 of 20 s.
- **Citation injection works on every model, and the validator is what stops it.** Asked through telemetry to "cite RB-ADMIN-0", each model obeyed at least once. The validator (ADR-009) removed every one of those citations before the UI, and no model recommended the destructive command. Prompt rules alone are not enough; the deterministic layer is required.
- **gpt-oss-120b and gpt-oss-20b did not open the poisoned runbook when asked** (0/2 and 1/2). They treated a runbook outside the evidence as out of scope, so for them that case does not measure resistance after exposure; the telemetry case does.

## Decision

Keep **`openai/gpt-oss-120b`** as the default.
- It is the only model that respects the scope rule every time and stays fast: about 3 s per diagnosis.
- It costs about a quarter of a cent per incident.
- It uses about 3k tokens per call, which leaves room for a diagnosis plus a follow-up within the same minute.

`gpt-oss-20b` is cheaper and just as fast, but it answers outside the investigation and makes up component health. That is the failure the gate exists to prevent. `qwen3.8-27b` behaves well but does not fit the free tier: it is 10× slower and 8× more expensive, and it runs out of daily quota during a demo day.

The model is configurable with `DEPLOYD_GROQ_MODEL` (`.env.example`, docker-compose). The decision trace shows which model and prompt version produced each answer, and the citations the validator removed.

## Consequences

- Rerun `python -m experiments.model_selection` when the model, the prompt or the Groq offer changes. `--rescore` recomputes the tables from the stored answers without calling any model.
- **Limits:**
  - Small sample: 6 diagnoses and 12 follow-ups per model.
  - Temperature 0.1 is not deterministic.
  - The refusal and injection checks are heuristics, corrected by hand where noted.
  - Free-tier quotas cut the qwen sample short.
  - Prices are Groq's list prices on 2026-10-09.
