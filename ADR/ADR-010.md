# ADR-010: Pipeline Unification — Single Live Path with Dual Trigger

**Date:** 2026-10-07
**Status:** Accepted

## Context

DeployD historically had two parallel investigation pipelines:

1. **Demo/simulator path** (`demo/app.py`, `EventSimulator`): built an `InvestigationRequest` via `BuildInvestigation`, maintained a `ComponentHealthTracker` per simulation run, and used an explicit `causal_parent_index` to wire causal edges manually. The CRASH_LOOP reactive trigger (DID-20) was wired here.

2. **Live API path** (`deployd/entrypoints/api.py`): used `CorrelateEventsUseCase` + `IncidentGraph` for correlation and triggered investigation only on `current_global_severity == "Critical"`.

The two paths diverged: DID-20's `ComponentHealthTracker` CRASH_LOOP trigger was **not wired into the live API**, creating a gap where a real crash-loop incident would be missed unless it also happened to reach `Critical` graph severity.

Additionally, the entrypoint (`api.py`) contained business logic directly (`_run_investigation`, `_longest_chain`, `_chain_rules`, `_fsm_state`), violating the AGENTS.md rule that entrypoints should only call application use cases.

## Decision

**Keep one pipeline in the live path.**

1. **`LiveInvestigation` use case** encapsulates all investigation logic: longest-chain extraction, FSM state replay, rules collection, retrieval, and orchestrator dispatch. `api.py` delegates entirely to `LiveInvestigation.execute(graph)`.

2. **Dual trigger in the live API**: `receive_event` fires a background investigation when **either**:
   - `compute_incident_severity(graph) == "Critical"` (graph-based severity trigger), **or**
   - `ComponentHealthTracker.process_event(event)` returns `trigger=True` (FSM-based CRASH_LOOP/CRASHING trigger, DID-20).

   Both conditions share a single `_auto_diagnosed_incident_id` cooldown guard to prevent duplicate investigations per incident.

3. **`BuildInvestigation` is retired from the live path.** The demo (`demo/app.py`) uses `EventSimulator` and `BuildInvestigation` for its offline, script-based scenario replay, which is an independent concern. The live API never calls `BuildInvestigation`.

4. **`_RetrievalStack.retriever` is typed as `RetrievalPort`** (not `HybridRetriever`). `HybridRetriever` is imported only for construction in `_get_retrieval()` (composition root responsibility). All downstream code — including `LiveInvestigation` — references only the port.

## Consequences

**Positive:**
- `api.py` contains no business logic; it only wires adapters, calls use cases, and formats HTTP responses.
- CRASH_LOOP trigger is active in the live path, matching the demo path's intended DID-20 behaviour.
- One `LiveInvestigation` use case is the single authoritative place for investigation logic; it is independently unit-testable with stub agent and stub retriever.
- No `deployd.adapters.*` imports appear under `deployd/application/`.

**Negative / trade-offs:**
- The demo path (`demo/app.py` / `EventSimulator`) and the live path still use different graph-building strategies (`BuildInvestigation` with explicit `causal_parent_index` vs. `CorrelateEventsUseCase`). Unifying the graph-building is left for a future iteration — it requires porting the scenario loader to emit events that `CorrelateEventsUseCase` can process without explicit parent wiring.
- The dual trigger (severity OR FSM) means an investigation can fire on CRASHING even without a full causal chain. `LiveInvestigation.execute()` correctly returns `None` in that case (no chain -> no investigation posted), so the trigger mismatch is gracefully handled.

- Supersedes the informal split between `demo/` pipeline and live API pipeline
