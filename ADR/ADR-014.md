# ADR-014: Peer Divergence — Which Change Separates the Failing Members of a Group

**Date:** 2026-10-12
**Status:** Accepted

## Context

A class of production incident the engine could not explain: ten identical instances behind a load balancer, a release that passed CI/CD and every test, and 500s on *some* instances only. The cause was an OS package upgrade that the platform had applied to those instances days earlier; their processes kept running on the old libraries until the release restarted them. The team suspected the release, rolled it back, and lost most of a working day.

Three things were missing:

- **Memory.** The window follows event time and keeps 5 minutes. The upgrade and the first error are hours apart, so no rule could ever see both.
- **A notion of "the same thing, many times".** Nothing said that `web-03` and `web-04` are interchangeable, so there was nothing to compare.
- **Change events.** Git pushes, CI jobs and host upgrades had no raw type, so they fell back to `STATE_CHANGE`.

## Decision

1. **Change events live longer than symptoms.** `SlidingWindow` keeps `CHANGE_EVENT_TYPES` (deploys, config and host changes) for `change_lookback_seconds` (24 h, `data/correlation_config.json`) and everything else for 5 minutes. No existing rule matches a change event, so none of them changes behaviour.
2. **Peer groups come from the events, not from a file.** A collector tags every event with `metadata.peer_group` (auto scaling group, target group, Beanstalk environment, workload: whatever the platform knows). The members are the components seen with that tag; no instance and no count is declared, so autoscaling needs no change. A first version declared the fleet in `components.json`; DID-44 removed it. Inferring a group from a shared caller would be wrong anyway: `api-gateway` calls auth, search and checkout, which are different services.
3. **RULE-07 (`domain/causal/peer_divergence.py`)** compares *who received which change* with *who is failing*. It names the change that every clustered failure carries and no healthy instance does; a change every instance received (the release) is reported as unable to explain the split. It emits a derived `PEER_DIVERGENCE_DETECTED` event, the same pattern as `CONFIG_DRIFT_DETECTED` (ADR-005), linked to the first symptom of each affected instance. The agent reads it as the root of the chain, so nothing new reaches it outside the evidence set.
4. **No package, OS or vendor in the engine.** The identity of a change is `change_kind` / `change_ref` in the event metadata, set by the collector. What the upgrade *did* is a Tier-3 hypothesis, grounded in the runbook; it is never a rule.
5. **Raw types** `GIT_PUSH`, `PIPELINE_JOB` (a job at least 2× slower than its own `avg_duration_ms` is a WARNING; no baseline, no verdict) and `HOST_UPGRADE`.
6. **Investigating a finding covers the members it names** (`chain_components`), so the UI does not report their small chains as left out. The UI scope warning follows the evidence of the investigation, not a declared list.

## The scenario

`data/scenarios/live_ec2_os_upgrade.json`, generated and seeded by `scripts/generate_ec2_scenario.py`: 935 events over 16.6 hours. A night patch window upgrades four of ten instances; a merge, a pipeline whose build is 2.9× its average, a rolling deploy; 500s on those four only behind a health check that keeps passing; a rollback that fixes nothing.

| | |
|---|---|
| Graph | 935 events → 16 nodes, 12 edges |
| Finding | at 10:54:56: 22 min after the first 500, 9 s after the last of the four began failing, 43 min before the rollback was started |
| Names | `os_upgrade patch-baseline-2026-10-07` on 4/4 failing, 0/6 healthy; `deploy 2.14.0` reached all 10 |
| Gate | Tier 3 FULL, best match 0.68 (`RB-FLEET-OS-UPGRADE-DIVERGENCE`) |
| Declared in `data/` | nothing: no instance, no load balancer, no group; the topology of the other scenarios is not needed (`gate.md`, "without topology": still FULL) |

One live run (gpt-oss-120b, 4.7k tokens) named the patch baseline, and after the wording fix below said the release cannot be the cause. That is a demonstration, not a measurement.

## A single instance (DID-48, RULE-08)

Peers need more than one instance. A lone instance is compared with itself over time (`domain/causal/change_contrast.py`): the window keeps, for hours, a thinned record of the changes in force at each failure (`SYMPTOM_OBSERVED`, derived by the use case). A change is **implicated** when it is constant across every recorded failure and was reported before the first; a change whose value **varied** while the entity kept failing is **ruled out**. It fires when a failure cluster completes on an entity without peers, and again when the candidates narrow. It is the same contrast as RULE-07, on time instead of peers.

Replayed on the same day reduced to `web-09` (`live_ec2_single_instance.json`, 206 events, no group tag):

| When | Finding |
|---|---|
| 10:54:56, first failure cluster (Critical, investigation opens) | `deploy 2.14.0` and `os_upgrade patch-baseline-2026-10-07` are both constant across every failure: **not separable yet** |
| 12:12, first failure after the rollback | the only change constant across every failure is the upgrade; `deploy 2.14.0 -> 2.13.9` changed while it kept failing, so it cannot be the difference |

**What cannot be done:** at the first symptom, the restart makes the new code and the new system libraries effective at the same moment. Nothing in one entity's timeline separates them; the rule says so and lists both. The rollback is what separates them. Without it (a test removes the rollback events) the two stay unseparated and the Tier-3 agent, with the runbook, has to weigh them. Against a peer group the same ambiguity does not arise: that is why RULE-07 exists.

Gate on the single-instance day: Tier 3 FULL, best match 0.54: only 0.04 above the threshold, because the finding is worded for one instance and the runbook for a group.

## Consequences

- **Wording matters to the model.** The first description said the deploy was "on all 10, excluded"; the agent answered that the failing instances had been "excluded from the deploy". It now says "reached all 10, so it cannot explain the split".
- **The runbook is ours.** We wrote the scenario and its historical runbook, so the match is a demonstration of the pipeline, not evidence of retrieval quality. Adding it to the corpus is measured in ADR-012: one query lost two ranks to it.
- **Limits.**
  - The finding needs a healthy sibling *seen working* in the last 5 minutes: silence is not health.
  - It fires once, when an instance completes its error cluster. If the evidence is incomplete at that moment (a sibling that has the change but has not failed yet), there is no finding and nothing retries it.
  - Instances with a few errors that carry the change count as affected; a few errors on one that does not are ignored; a clustered failure the change does not explain means no finding. Two changes that separate the groups are both reported.
  - Peer membership and change identity depend on the collector tagging events (`peer_group`, `change_kind`); free text is never compared. An untagged instance has no peers.
  - The agent sees the first 200 characters of the description: the instance names and the separating change come first.
  - 500s do not move the process-health FSM: `web-09` stays HEALTHY, its process runs and its shallow health check passes. The peer comparison is the only signal.
  - Changes and failure records are held in memory for 24 h; there is no persistence.
  - RULE-08 needs a change reported before the first recorded failure and tagged with `change_kind`; a failure that predates every change implicates nothing.
