# ADR 007

## Why retrival is hybrid and not only embedding

Starting point: system needs to find relevant historical runbooks when a new incident arrives. Easiest choice would've been to dump evth in Chroma, do cosine similarity and call it a day.

Problem is that embeddings work great (currently using `all-MiniLm-L6-v2`) but until the text describes the problem in a narrative way. But in our domain it happens pretty often that the root cuase is an exact identifier , sometimes ending up close in the vector space sometimes not.
That is not an acceptable risk to undertake.

## BM25
Is an "stupid" algorithm in a way. It counts words, weights them by reverse frequency. If the runbook has written 'libssl' exactly, it finds it, done, there is nothing to understand. Its the natural complement of embeddings: one captures the semantic similarity the other the exact corresponding keywords.
Keeping them separate in `ChromaRunbookClient` and `BM25RunbookIndex` each producing their hits and fuse later.

## Graph structure

This part justifies all the work on the incident graph, distinguishing this system from a generic RAG. Two incidents can be completley different semantically, but have the same identic form : deploy -> crash -> restart. same services involved. Text alone dose not catch this.

So GraphIndex works on structures, not on text:
**Casual chain similarity:** take sequence of the current incident events and confronts it with the one of historical runbooks using Longest Common Subsequence (LCS) normalized on the length of the longest chain. If two incidents have the same sequence of events in the same order, the signal is very strong.
**Component overlap:** Jaccard on involved components. Two incidents touching same servies have a correlation, even if the signal by itself is weak.

Structures are stored in GraphStore in memory - each `RunbookStructure` has its `runbook_id`, `causal_chain` (ordered tuple of events), and `affected_components` (frozenset).

### Fusion
The four scores are merged in `similarity.py` with a weighted mean.

**Signals weights:**            **Why**
- semantic(chroma): 0.35    |   Catches significant semantic, useful for description
- bm25: 0.20                |   Essential for exact keyword matches.
- causal(LCS): 0.30         |   Same causal chain of events = strong signal.
- component(Jaccard): 0.15  |   Correlation signal, not strong enough to be a top one.

Total 1.0 . Honestly this weights are thought but not validated. Will be tuned.

### What was dumped

- **Embeddings only**: Too unreliable for this domain.
- **Bm25 only**: misses paraphrasing and rewording.


### Status: Accepted
Works, is testable, each piece is isolated in its adapter. If weights are wrong we just change 4 constants. If we need a fifth signal we can add it and rebalance. Overall i think this structure holds for this project.
