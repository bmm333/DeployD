# ADR-006: Process Health FSM - Deterministic Finite State Machine

## Status
Proposed

## Context

`ProcessHealthFSM` turns a chronologica stream of `CoreEvent`s into a process health state, used to detect crash loops deterministically, without probabilistic scoring or an LLM in the loop
We rejected to frame it as a formal textbook DFA (Deterministic finite automaton). This FSM actual next state depends not only on curr state and input symbol but also depends on bounded restart history and configured thesholds. So forcing this into a pure DFA is not a good idea, it would either hide that dependency or lead to a fake symbol.

## Decision

Model `ProcessHealthFSM` as a deterministic finite state machine with bounded auxiliary history not a pure DFA.
 ` next_state=fi(curr_state,event,restart_history,configuration) `
 States (Q):
 ` HEALTHY, DEGRADED, CRASHING, RESTARTING, CRASH_LOOP `
 `INITIAL STATE: HEALTHY `
 ` Event classes (sigma or our "alphabet") derived from CoreEvent not raw CoreEventType:`
 `
| Class | Condition |
|---|---|
| WARN | severity=WARNING, type in {RESOURCE_EXHAUSTION, HEALTH_CHECK_FAIL} |
| CRIT_FAIL | severity=CRITICAL, type in {PROCESS_CRASH, DEPENDENCY_FAILURE} |
| CRIT_CRASH | severity=CRITICAL, type = PROCESS_CRASH (subset of CRIT_FAIL) |
| RESTART | type = DEPLOY_STARTED, or type = STATE_CHANGE with metadata marking a restart attempt |
| RESET | type = HUMAN_OBSERVATION with metadata.action = MANUAL_RESET `

` any event that dose not match none of those is unclassified and is a no op in every state`
`Timer is explicitly not an event class` there is no CoreEventType.Timer


### Transition table

| State | WARN | CRIT_FAIL | CRIT_CRASH | RESTART | RESET |
|---|---|---|---|---|---|
| HEALTHY | → DEGRADED | → CRASHING | → CRASHING | no-op | no-op |
| DEGRADED | no-op | → CRASHING | → CRASHING | no-op | no-op |
| CRASHING | no-op | no-op | no-op | → RESTARTING* | no-op |
| RESTARTING | no-op | no-op** | → CRASHING | → RESTARTING* / → CRASH_LOOP*** | no-op |
| CRASH_LOOP | no-op | no-op | no-op | no-op | → HEALTHY |

`*` Restart while crashing or RESTARTING records a restart attempt
 `**` CRIT_FAIL that is not specifically crit crash while restarting is a no op a dependency failing dose not neccessarily mean the restart itself failed , `***` Wether a restart attempt yields RESTARTING or CRASH_LOOP is guarded by the restart counter.

 For Any event recived while in Restarting: if the recovery window has elapsed since the most recent restart attempt the fsm transitions to healthy fisrt , before any class based rule is evaluated, except a crit crash which always takes priority over the timer guard.

 ### Guard conditions

| Guard | Condition |
|---|---|
| Restart recorded, stay RESTARTING | `len(restart_timestamps) <= max_restart_count` after pruning entries older than `restart_time_window` |
| Restart recorded, promote to CRASH_LOOP | `len(restart_timestamps) > max_restart_count` after pruning |
| RESTARTING → HEALTHY | `event.timestamp - restarting_since >= recovery_window` |
| CRASH_LOOP → HEALTHY | only via RESET; restart history is cleared |

## Consequences:
- The table is small to be the literal source of truth for the test suite
- No invented event types, every guard is tracable to existing fields.

## Negative/Trade-offs:
- `DEGRADED` has no defined path back to `HEALTHY` without a full
  `CRASHING → RESTARTING → recovery` cycle, even if the warning
  condition self-resolves. Left open deliberately rather than guessed;
  revisit if it proves wrong in practice.
- The FSM only re-evaluates time-based guards when a new event arrives —
  a process stuck in `RESTARTING` with no further events will never
  reach `HEALTHY` on its own. If real-time recovery detection is needed,
  the orchestrator must feed a periodic synthetic/health-check event;
  this is deliberately an application-layer concern, not the FSM's.
