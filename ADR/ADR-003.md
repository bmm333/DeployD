## Graph Representation and Relationships

## Context
When an incident happens in a system, individual events such as logs, metrics, crashes are generated, and usually not in isolation. Therefore our model should reason about an "incident" in a programmatical way (feeding this context to an LLM for diagnosis), so we need a Data Structure capable to map the causal and temporal relationships between events.

## Decision
Using Directed Graph structure to model incidents within the domain.
Foundamental layers of the graph:
1. Node (Fact): It rappresents a single , immutable, observed domain event (such as PROCESS_CRASH or DEPLOY_FAILED). A Node is not an abstract concept, it must always trace back to a concrete CoreEvent.
2. Edge (relationship): An edge is a directional link representing the relationship between a source Node and a target Node. It defines how two entities are related using `EdgeType`. Because systems are complex, causality is often inferred rather than guaranteed. So every Edge must carry a confidence score (0.0-1.0) and a time_to_delta to quantify the probability of the relationship.
3. Aggregation - Graph: as per graph theory: A Graph is a collection of nodes and edges where edges connect nodes. In our domain, a Graph aggregates all nodes and edges related to a specific incident window. It provides the structural API's required to traverse the incident, finding root causes or ultimate resulting failures (leaf nodes). We reasoned this because our system this way can construct a deterministic timeline of an incident before handing it over to LLM.

## Consequences (hypotheticaly this will be updated once we have a running version to test if our hypotheses are correct)
- Positive: the system can deterministically  identify root causes by backtracking from a failure node (leaf node). AI agents will recive a structured context, not raw logs.
- Negative: Graph structures can be heavy to sort and traverse in memory for long incidents. Must set boundaries for incident windows.
