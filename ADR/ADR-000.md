# Observing

Something goes wrong within our system . The system emits raw signals (the real world example from my friend that set me up for building deployd)
MongoDb Election Scenario

our system enforces chronologica order of events im not writing a fully blown table here for semplicity so assume an interval of (1-10] seconds between events

1. MongoDb primary ip-10-0-1-4 crashes. Replica set logs: `Replica set primary stepped down` Source: MongoDb logs . Adapter: CloudWatch adapter (polling logs)
2. New primary elected Log: `Transition to Primary Completed`. MongoDb logs. Adapter: Cloud watch
3. API Attempts write to old primary. Gets NotPrimary error. Logs: `MongoError: NotPrimary`. App logs. Log scrapper adatper.
4. Api Returns 202 Accepted to the clinet, no error to Sentry (or whatever). App logs. Log scrapper adapter (silent failure detection)
5. VM monitor detects connection pool errors. ss -tunap shows failed connections. VM state. Vm adapter as adapter.

Where each adapter is polling its source of truth detecting a  change and converts it into a standardized incoming event (DTO's will be VERY handy here) As mentioned in other adr for the events see `ADR-003.md` i think. We feed the core event into the process health fsm, where fsm tracks its process vitality, not root causes. in this specific scenario the FSM never transitions to CRASHING because the process never crashed since the process is still running and returning 202's
