# ADR-015: A Read-Only MCP Server on Top of the API

**Date:** 2026-10-14
**Status:** Accepted

## Context

The decision trace, the causal graph and the runbook lookups are useful to an engineer who is already talking to an assistant (Claude Desktop, Claude Code, an Agno agent). The Model Context Protocol is the standard way to hand such an assistant tools. DID-40 asked for a small server that exposes read-only tools and nothing else.

Two facts shape it. The live incident (graph, decision trace, review) lives in the memory of the API process, so a separate process cannot read it through the application use cases. And AGENTS.md forbids executing anything: the system suggests, engineers approve.

## Decision

1. **A thin client of the API, over stdio** (`deployd/entrypoints/mcp_server.py`, official `mcp` SDK, `FastMCP`). It imports `httpx`, `mcp` and `pydantic` and nothing from the project: no state, no business logic, no domain. It runs as its own process next to the API: `python -m deployd.entrypoints.mcp_server [--api-url ...]` (also `DEPLOYD_API_URL`).
2. **Five tools, every one a `GET`**, each declared read-only (`readOnlyHint`, not destructive, idempotent):
   `list_incidents`, `get_incident_state` (live severity, causal graph with the rule of each edge, the diagnosis under review), `get_decision_trace` (live, or a past incident with its human decisions), `search_runbooks`, `check_component_dependencies`.
   Nothing approves, rejects, resets or sends: the engineer decides in the UI. The LLM that reads the answers is the client's; the server calls none.
3. **Two new read-only endpoints in the API** (`GET /api/v1/runbooks/search`, `GET /api/v1/components/{component}/compatibility`), because the retrieval stack and the registry live in the composition root. They reuse the agent's `ComponentInput` / `DependencyCheckResult` and the hybrid retriever; the component registry is now built once and shared with the agent.
4. **Inputs validated twice**: by the tool signatures (length of a query, the shape of a component name and of an incident id: a path such as `../state` never becomes a request) and again by the API.
5. **Text from logs is marked as data.** Event descriptions and runbook text can be influenced by whoever writes logs, and the answers go to someone else's model. Every answer carries a note saying so, labels are cut to the 200 characters the agent itself sees, and the server's instructions say none of the tools changes anything.
6. **`mcp` is an optional extra**, not a runtime dependency: `pip install -e ".[mcp]"`. It is in `requirements-dev.lock` (7 packages added: `mcp` 1.30.0 and its `cryptography`, `cffi`, `pycparser`, `pyjwt`, `httpx-sse`, `sse-starlette`; no existing pin moved), so CI tests it; `requirements.lock` and the Docker image are unchanged. Version 2 of the SDK exists but pulls a different HTTP stack: pinned to `<2`.

## Alternatives considered

- **Mount the MCP app inside the FastAPI process** (streamable HTTP). It would share the state directly, but couples the protocol to the API process and needs a remote-capable client; Claude Desktop and Claude Code speak stdio natively.
- **Call the application use cases from a separate process.** Closed incidents are in SQLite, but the live graph and the pending review are not: the one thing worth asking about would be missing.
- **Write tools (approve, reset).** Out of scope by design, and an assistant acting on log text it has just read is exactly the risk the gate exists to avoid.

## Measured

- 16 tests drive the server through a real MCP session against the real API (list, call, errors), 7 more test the two endpoints; a test records every request the server makes and asserts they are all `GET`.
- The tests were checked by breaking the server: `POST` instead of `GET` fails 12 of 16, dropping the note fails 4, not cutting labels fails 1.
- A stdio client (`mcp.client.stdio`) against a live API loaded with the EC2 day: 5 tools listed, the peer-divergence finding and the Tier-3 trace read back, a path-like component name refused.
- `pip-audit` on the 7 added packages: no known vulnerabilities (2026-10-14).

## Consequences and limits

- **No authentication.** The API has none and the server trusts whoever launches it; stdio means a local process. Not a deployment story.
- **Prompt injection is reduced, not removed.** The note and the cut labels help a careful client; a client that obeys text in tool results can still be misled. The threat model in `prompts/README.md` covers our agent, not someone else's.
- **Search scores run low on text alone.** `search_runbooks` has no causal chain, so the right runbook scored 0.415 against the gate's 0.5 on the EC2 day (rank 1). The tool says so; judge by rank.
- **The CI audit covers the runtime lock only**; the `mcp` extra was audited by hand.
- **It needs the API running.** A closed API gives a clear tool error, not a crash. It runs on the host, not in the compose stack.
- It adds no detection and no analysis: it is an interface. Its value is that the engine's evidence is reachable from the assistant an engineer already uses.
